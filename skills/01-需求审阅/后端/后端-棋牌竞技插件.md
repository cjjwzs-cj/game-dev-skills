# 棋牌/竞技 后端专项审阅插件

## 适用场景
策划案涉及以下内容时自动加载：
- 房间创建/销毁
- 匹配系统
- 段位、ELO 分
- 牌局、结算
- 棋牌规则（麻将、扑克）
- 竞技场

## 后端必查清单

### 1. 房间系统

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 房间ID | 房间ID生成规则？是否全局唯一？ | 建议 `server_id + timestamp + seq` |
| 房间超时 | 房间无人时多久销毁？ | 明确：通常 5-10 分钟 |
| 房主转移 | 房主离线/退出时是否自动转移？转给谁？ | 明确：按加入顺序或随机 |
| 房间密码 | 是否需要密码？如何验证？ | 明确安全方案 |
| 房间配置 | 牌局规则（局数、底分）是否可配置？ | 明确配置项和范围 |
| 观战模式 | 是否支持观战？观战人数上限？ | 明确 |

### 2. 匹配系统

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 匹配池 | 匹配池的大小？峰值同时匹配人数？ | 预估容量 |
| 匹配算法 | 段位差距多少内可匹配？ | 明确 ELO 差值阈值 |
| 超时扩展 | 匹配超时后是否放宽条件？放宽几次？ | 明确：每 X 秒扩大 Y 分 |
| 匹配取消 | 匹配中是否可以取消？取消有无惩罚？ | 明确规则 |
| 跨服匹配 | 是否支持跨服匹配？数据如何同步？ | 明确架构 |
| 匹配队列 | 同一玩家是否可以同时进入多个匹配队列？ | 禁止，防止状态混乱 |

### 3. 牌局/竞技

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 规则验证 | 牌局结果由服务器全量计算还是客户端上报？ | 必须服务端全量计算，防止作弊 |
| 回合超时 | 每回合操作时间限制？超时怎么处理？ | 明确：托管或弃权 |
| 断线重连 | 断线后多久内可重连？重连后能否继续？ | 明确：保留牌局状态 X 分钟 |
| 托管/AI | 玩家断线后是否自动托管？AI 强度？ | 明确 |
| 牌局记录 | 每局牌局是否保存？保存多久？ | 明确，通常 30-90 天 |
| 回放功能 | 是否支持战局回放？如何存储？ | 明确技术方案 |

### 4. 结算系统

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 计分公式 | 胜负如何计分？底分倍数？ | 明确公式 |
| 段位分变化 | 胜利/失败后段位分变化公式？ | 明确：ELO 或自定义公式 |
| 掉线结算 | 玩家中途掉线，最终怎么结算？ | 明确：按已进行局数结算或判负 |
| 奖励发放 | 金币/道具奖励何时发放？ | 原子操作：结算 → 加奖励 |
| 重复结算 | 结算接口是否幂等？ | 需要 request_id 去重 |

### 5. 段位/ELO 系统

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 初始分 | 新玩家初始段位分？ | 明确数值 |
| K 值 | ELO 的 K 值（变化幅度）是多少？ | 明确，新手期可不同 |
| 段位区间 | 每个段位对应的分数区间？ | 明确表格 |
| 段位保护 | 新晋级后是否有保护期不掉段？ | 明确：通常 X 局保护 |
| 赛季重置 | 赛季结束后段位如何重置？ | 明确规则（按比例衰减） |
| 领奖资格 | 达到特定段位才能领奖，如何防止刷分？ | 领奖时加锁，防止并发 |

### 6. 反作弊（棋牌重点）

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 牌堆随机 | 牌堆随机数种子来源？是否真随机？ | 服务器生成种子，防止客户端预测 |
| 观战透视 | 观战者能否看到所有玩家的牌？ | 明确：观战可设置延迟或遮挡 |
| 异常检测 | 异常胜率、异常操作的检测？ | 明确检测规则和处罚措施 |
| 第三方辅助 | 是否有防止模拟点击、脚本的方案？ | 行为检测 + 验证码 |
| 恶意托管 | 托管送分如何检测？ | 托管次数限制 + 异常检测 |

### 7. 性能专项

| 检查点 | 问题 | 建议 |
|--------|------|------|
| 房间压力 | 同时在线房间数上限？ | 预估容量 |
| 匹配压力 | 匹配算法 O(n²) 在万级匹配池是否可行？ | 预估耗时 |
| 广播压力 | 牌局内操作广播到所有玩家，带宽预估？ | 每局 N 人，每秒 M 次操作 |
| 数据库压力 | 每局结算写一次 DB，峰值 TPS 多少？ | 预估 + 异步写入 |

## 输出格式

### 标准输出格式

| 优先级 | 序号 | [棋牌]模块 | 问题描述 | 建议补充/修改 |
|--------|------|-----------|----------|----------------|
| P0 | 1 | 房间系统 | 无房间超时销毁机制，房间无限堆积 | 房间空置 X 分钟后自动销毁 |
| P0 | 2 | 反作弊 | 牌局结果依赖客户端上报 | 改为服务端全量计算 |
| P0 | 3 | 结算系统 | 结算接口无幂等，重复请求会多发奖励 | 增加 request_id 去重 |
| P1 | 4 | 匹配系统 | 匹配池容量未预估 | 评估峰值匹配人数 |
| P1 | 5 | ELO 系统 | K 值未定义 | 明确新手期和正常期 K 值 |

### 输出要求
- 按优先级排序：P0 → P1 → P2
- 每个问题必须包含：问题描述、建议修改
- 模块必须包含 `[棋牌]` 标签

### 无问题输出格式
如果未发现问题，输出：
```
✅ 棋牌/竞技 后端专项检查通过，未发现明显问题

检查模块：
- ✅ 房间系统
- ✅ 匹配系统
- ✅ 牌局/竞技
- ✅ 结算系统
- ✅ 段位/ELO 系统
- ✅ 反作弊（棋牌重点）
- ✅ 性能专项
```

## 边界情况处理

### 策划案内容不完整
- **情况**：策划案只包含部分棋牌竞技功能描述
- **处理**：基于现有内容审阅，输出警告提示可能遗漏的检查点

### 牌型规则不明确
- **情况**：策划案未明确具体的牌型规则（麻将/扑克的具体规则）
- **处理**：在问题描述中标注，建议明确牌型规则，不同规则对逻辑和性能有不同要求

### 房间规模不明确
- **情况**：策划案未明确房间规模（人数、局数）
- **处理**：在问题描述中标注，建议明确房间规模，以便评估性能和存储需求

### ELO算法不明确
- **情况**：策划案未明确ELO算法的具体实现（K值、初始分、衰减规则）
- **处理**：在问题描述中标注，建议明确ELO算法，不同算法对段位分布和玩家体验有不同影响
